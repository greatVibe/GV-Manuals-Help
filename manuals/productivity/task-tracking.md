# Task Tracking

Use this guide when turning work, requests, meeting outcomes, or follow-up items into tasks that can be tracked clearly.

Good task tracking helps people know what needs to happen, who owns it, when it is due, and whether it is blocked.

## What Makes A Good Task

A good task is clear enough that the owner can complete it without guessing.

A useful task includes:

- A short title.
- A clear outcome.
- One owner.
- A status.
- A due date, if needed.
- Any important context.
- Any dependency or blocker.

If a task needs several separate outcomes, split it into smaller tasks.

## Write Clear Task Titles

Task titles should describe the action and the object.

Clear task titles often start with action words such as:

- Review.
- Draft.
- Send.
- Confirm.
- Update.
- Prepare.
- Check.
- Approve.
- Fix.
- Follow up.

Avoid vague titles such as urgent, check this, update, next steps, or issue unless the rest of the task explains exactly what is needed.

## Define The Outcome

Every task should make the expected result clear.

Ask:

- What should be true when this task is complete?
- What should the owner produce or change?
- Who needs the result?
- How will completion be recognised?

Examples of outcomes:

- A reviewed document with comments added.
- A corrected spreadsheet ready to share.
- A confirmed date sent to the team.
- A list of issues returned for review.
- A final file exported as a PDF.

## Assign One Owner

Each task should have one owner responsible for moving it forward.

Other people may contribute, but one person should be accountable for progress.

If ownership is unclear, mark the task as needing assignment rather than assuming someone will pick it up.

## Use Simple Statuses

Use statuses that are easy to understand.

Common statuses include:

- Not started.
- In progress.
- Waiting.
- Blocked.
- Ready for review.
- Complete.
- Cancelled.

Avoid too many status options. A small set is easier to keep accurate.

## Set Due Dates Carefully

Add a due date when timing matters.

Use a due date when:

- Another task depends on the result.
- A customer or stakeholder is waiting.
- The task affects a deadline.
- The work must be reviewed before a meeting.
- The task could otherwise be forgotten.

If there is no real deadline, it may be better to use a priority or review date instead of a false due date.

## Track Dependencies

A task may depend on another person, decision, file, or piece of information.

Record dependencies clearly, such as:

- Waiting for a document.
- Waiting for review.
- Waiting for a decision.
- Waiting for data.
- Waiting for confirmation.

A task that depends on something else should not look like normal in-progress work.

## Record Blockers

A blocker is something that prevents the task from moving forward.

For each blocker, record:

- What is blocking the task.
- Who can help remove the blocker.
- When it was identified.
- Whether it affects other tasks.
- What follow-up is needed.

Review blocked tasks regularly so they do not sit unnoticed.

## Add Useful Context

A task should include enough context for the owner to act.

Useful context may include:

- Relevant files or links.
- Background notes.
- Related decisions.
- Requirements or constraints.
- Review instructions.
- Known risks.

Keep context short. If the task needs a long explanation, link to the supporting document instead.

## Review Task Lists

Task lists become stale if they are not reviewed.

During review, check:

- Completed tasks can be closed.
- Blocked tasks still need attention.
- Due dates are still accurate.
- Owners are still correct.
- Duplicate tasks can be merged.
- Large tasks should be split.
- Cancelled tasks are marked clearly.

A clean task list is easier to trust.

## Closing A Task

Before marking a task complete, confirm that the expected outcome has been met.

Check:

- The work is finished.
- The result has been shared, if needed.
- Any review comments have been addressed.
- Any related files are in the right place.
- Follow-up tasks have been created if needed.
- The task notes are clear enough for later reference.

Do not close a task only because work has started or because someone replied.

## When To Ask For Review

Ask for review when:

- The task affects another person or team.
- The task changes a shared file or report.
- The task affects a customer, financial, legal, or operational outcome.
- The owner is unsure what complete means.
- The due date or priority is unclear.
- The task is blocked and needs a decision.

## Quick Checklist

Before relying on a task list:

- Each task has a clear title.
- Each task has one owner.
- Important tasks have due dates or priorities.
- Blockers and dependencies are visible.
- Statuses are up to date.
- Large tasks are split into smaller tasks.
- Completed tasks are closed only after the outcome is met.
- Follow-up tasks are created when needed.
