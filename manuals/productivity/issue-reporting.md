# Issue Reporting

A clear issue report helps someone understand what went wrong, why it matters, and what information is needed to fix it. Good issue reports reduce back-and-forth and make it easier to prioritize work.

This guide explains how to write practical issue reports for documents, spreadsheets, files, workflows, reviews, approvals, exports, and other productivity work.

## When to use this guide

Use this guide when you need to report:

- An error in a document or spreadsheet.
- A broken link or missing file.
- A confusing instruction or unclear process.
- A formatting problem.
- A file sharing or access problem.
- A missed deadline or blocked task.
- A data mismatch or validation issue.
- A repeated problem that needs a durable fix.
- A request that cannot move forward without a decision.

An issue report does not need to be long. It needs to be specific enough that someone else can understand and act on it.

## Start with a short title

The title should describe the problem in plain language.

Good titles:

- Missing approval date in monthly summary
- Export file opens with broken formatting
- Duplicate rows in customer list
- Review link is not accessible
- Spreadsheet total does not match source data

Avoid vague titles:

- Problem
- Issue
- Broken
- Help
- This is wrong

A useful title lets readers understand the issue before opening the full report.

## State the problem clearly

Use the first paragraph to explain what is wrong.

Include:

- The affected file, document, task, or process.
- What you expected to happen.
- What actually happened.
- Whether the issue blocks work.

Example:

The April summary spreadsheet shows a total of 125 in the overview tab, but the source data adds up to 118. This blocks final approval because the reviewer cannot confirm which number is correct.

Keep the problem statement factual. Avoid blame or speculation unless you have confirmed the cause.

## Include where the issue appears

Tell the reader exactly where to look.

Useful location details include:

- File name.
- Folder or shared location.
- Page or section.
- Tab name.
- Row or column.
- Slide number.
- Link name.
- Task title.
- Date or version.

Examples:

- File: Monthly summary draft
- Tab: Overview
- Row: 18
- Section: Approval notes
- Version: April 8 review version

Precise locations save time and reduce misunderstanding.

## Explain the impact

Impact helps the owner understand urgency and priority.

Useful impact statements include:

- This blocks approval.
- This may cause the wrong file to be shared.
- This could confuse external readers.
- This prevents the task from being completed.
- This affects only formatting and does not change the content.
- This affects one row, not the full spreadsheet.

Avoid overstating the impact. If the issue is minor, say so.

## Add steps to reproduce when useful

For issues that happen when someone follows a process, include steps.

Example:

Steps to reproduce:

1. Open the shared spreadsheet.
2. Go to the Summary tab.
3. Filter the Status column to Approved.
4. Compare the total with the Overview tab.

Expected result:
The filtered total matches the overview total.

Actual result:
The overview total is higher by 7.

Steps are especially useful for access problems, export problems, formatting problems, or repeated process issues.

## Include evidence

Evidence helps the owner confirm the problem quickly.

Useful evidence includes:

- A screenshot.
- A copied error message.
- The affected row or section name.
- A small example of the mismatch.
- A link to the relevant file, if safe to share.
- The date and time when the issue happened.

Do not include private or sensitive information unless it is necessary and approved.

## Separate facts from assumptions

Facts are things you have confirmed. Assumptions are possible explanations.

Example:

Facts:
- The total in the overview tab is 125.
- The source rows add up to 118.
- The file was exported on April 8.

Assumption:
- The overview total may include hidden rows.

Separating facts from assumptions helps prevent the wrong fix.

## Name the requested outcome

Say what you need from the owner.

Examples:

- Please confirm the correct total.
- Please restore access for the reviewer.
- Please update the link in the summary.
- Please decide whether the duplicate rows should be removed.
- Please confirm whether the file should be shared as a PDF or spreadsheet.
- Please review and approve the corrected version.

If you are not sure what action is needed, ask for triage.

## Add priority without exaggeration

Priority should be based on impact and timing.

Simple priority labels:

- Urgent: Work is blocked or a deadline is at risk.
- High: Important work is affected, but there is a workaround.
- Normal: The issue should be fixed, but work can continue.
- Low: Minor issue or improvement.

Include a due date when timing matters.

Example:

Priority: High
Needed by: April 10
Reason: The summary is scheduled for final approval on April 11.

## Assign an owner when known

If you know who should handle the issue, name the owner.

Examples:

- Owner: Document reviewer
- Owner: Reporting team
- Owner: Project lead
- Owner: File owner
- Owner: To be assigned

If ownership is unclear, write: Owner needed.

## Keep private information out of public reports

Issue reports are often shared, copied, linked, and summarized.

Avoid including:

- Passwords or access tokens.
- Private customer details unless required and approved.
- Sensitive personal information.
- Internal notes that should not be shared.
- Links that readers should not be able to access.
- Unrelated message history.

When sensitive detail is necessary, summarize the safe issue and store the sensitive material in the appropriate secure location.

## Update the issue as work progresses

An issue report should show the current state.

Useful status values include:

- Open: The issue is reported but not resolved.
- In progress: Someone is working on it.
- Waiting: More information or approval is needed.
- Resolved: The issue has been fixed.
- Closed: No further action is needed.

Add short updates instead of rewriting the full report.

Examples:

- April 8: Issue reported. Total mismatch found in Overview tab.
- April 9: Source rows reviewed. Hidden rows identified.
- April 9: Total corrected and sent for approval.
- April 10: Approved version shared.

## Close with the resolution

When the issue is fixed, record what changed.

Include:

- What was fixed.
- When it was fixed.
- Who confirmed it.
- Any follow-up work.

Example:

Resolution:
The hidden rows were removed from the overview total on April 9. The corrected total is 118. The reviewer confirmed the fix, and the file is ready for final approval.

If the issue was not fixed, explain why it was closed or deferred.

## Issue report template

Use this template for a simple issue report.

Title:
[Short problem title]

Status:
[Open, in progress, waiting, resolved, or closed]

Priority:
[Urgent, high, normal, or low]

Owner:
[Person or team, or write Owner needed]

Reported date:
[Date]

Affected item:
[File, document, task, process, or link]

Problem:
[What is wrong]

Expected result:
[What should happen]

Actual result:
[What happened instead]

Impact:
[Why it matters]

Location:
[Section, page, tab, row, link, or version]

Evidence:
[Screenshot, example, error message, or safe link]

Requested outcome:
[What you need]

Updates:
- [Date: short update]

Resolution:
[What fixed the issue, or why it was closed]

## Example issue report

Title:
Spreadsheet total does not match source data

Status:
Open

Priority:
High

Owner:
Reporting team

Reported date:
April 8, 2026

Affected item:
Monthly summary spreadsheet

Problem:
The overview tab shows a total of 125, but the source rows add up to 118.

Expected result:
The overview total should match the source data total.

Actual result:
The overview total is higher by 7.

Impact:
This blocks final approval because the reviewer cannot confirm which number is correct.

Location:
Overview tab, total row. Source data tab, approved rows.

Evidence:
The mismatch appears when filtering the source data to approved rows.

Requested outcome:
Please confirm the correct total and update the overview tab.

Updates:
- April 8: Issue reported after review.

Resolution:
Pending.

## Quick checklist

Before sending an issue report, confirm that:

- The title describes the problem.
- The affected item is named.
- The problem is factual.
- Expected and actual results are clear.
- The location is specific.
- The impact is stated.
- The requested outcome is included.
- Priority matches the impact.
- Ownership is named or requested.
- Private information is not exposed.
- The report can be understood by someone who was not present.

## Key takeaway

A strong issue report makes a problem easy to understand and act on. State what is wrong, where it appears, why it matters, what evidence supports it, and what outcome is needed.
