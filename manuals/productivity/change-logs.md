# Change Logs

A change log records what changed, when it changed, and why it matters. It helps people understand the history of a document, file, report, process, or project without comparing every version manually.

This guide explains how to keep clear change logs for productivity work, shared files, documents, spreadsheets, reviews, and recurring operations.

## When to use this guide

Use this guide when you need to:

- Track changes between file versions.
- Summarize updates after review.
- Record what changed before approval.
- Explain differences between drafts.
- Maintain a history for a recurring report.
- Prepare release notes for a non-technical audience.
- Help someone understand what is new, fixed, removed, or still pending.

A change log is useful whenever people need confidence about what changed and whether anything important still needs attention.

## Keep the purpose simple

A change log should answer four questions:

- What changed?
- Why did it change?
- When did it change?
- Who needs to know?

It does not need to include every small edit. Focus on changes that affect readers, reviewers, users, or future work.

## Use clear categories

Categories make a change log easier to scan.

Common categories include:

- Added: new content, rows, sections, files, or features.
- Changed: updates to existing content, structure, wording, or data.
- Fixed: corrections to errors, broken links, wrong totals, or formatting issues.
- Removed: deleted content, outdated sections, duplicate rows, or unused material.
- Pending: known work that is not complete yet.
- Notes: context that helps explain the change.

Use only the categories that fit the work.

## Write changes as outcomes

A change log should describe the result, not only the activity.

Prefer:

- Added a summary section for the March report.
- Corrected the total in row 18 to match the source spreadsheet.
- Removed duplicate customer rows from the export file.
- Updated the approval deadline from Thursday to Friday.

Avoid:

- Worked on report
- Made edits
- Updated file
- Fixed stuff

The reader should understand what is different after the change.

## Include dates consistently

Dates help readers understand sequence and recency.

Use one date format throughout the change log. For example:

- 2026-04-08
- April 8, 2026
- Apr 8, 2026

Choose the format that fits your audience and use it consistently.

For recurring reports or versioned files, include the date beside each entry or group changes by date.

## Include version names when useful

Versions are helpful when several drafts or files exist.

Useful version labels include:

- Draft 1
- Draft 2
- Review version
- Approved version
- Final version
- Version dated April 8

Avoid vague version names such as latest, final final, or new copy. Use a label that will still make sense later.

## Explain why important changes were made

Some changes need a short reason.

Add a reason when the change affects:

- Meaning.
- Scope.
- Deadline.
- Data interpretation.
- Review outcome.
- Customer-facing content.
- Future work.

Example:

Changed the status label from complete to needs review because two approval comments are still open.

You do not need to explain routine spelling or formatting corrections unless they matter to the review.

## Link changes to feedback or decisions

When a change came from feedback, approval, or a decision, record that connection.

Examples:

- Updated the introduction based on reviewer feedback from April 8.
- Removed the optional appendix after the approval meeting.
- Deferred the chart redesign to the next version after the team chose option B.

This helps people understand why a change happened and prevents repeated discussion.

## Separate completed changes from pending work

Do not mix finished changes with planned work.

Completed:
- Added the review checklist.
- Corrected the February total.
- Removed duplicate rows.

Pending:
- Confirm the April figure.
- Add final approval date.
- Export the PDF after review.

This makes the current state easier to understand.

## Record removed items carefully

Removed content can matter later. When you remove something important, explain what was removed and why.

Examples:

- Removed the outdated pricing example because it no longer matches the current process.
- Removed duplicate rows that appeared in both the March and April exports.
- Removed internal notes before sharing the file externally.

This prevents confusion when someone expects to find content that is no longer present.

## Keep entries short

Most change log entries should be one sentence or one bullet.

Include only:

- The changed item.
- The outcome.
- The reason, if useful.
- The source of the change, if useful.

Move long explanation into the related document, approval note, or project summary.

## Match the detail to the audience

Different audiences need different change log detail.

For reviewers, include:

- What changed since the last review.
- Which comments were resolved.
- What still needs review.

For team members, include:

- Work completed.
- Data or content updates.
- Open tasks.
- Follow-up owners.

For customers or external readers, keep the log factual, concise, and free of internal notes.

## Protect private information

Change logs are often copied into summaries, approvals, or release notes.

Avoid including:

- Passwords or access tokens.
- Private customer data unless required and approved.
- Internal notes that should not be shared.
- Sensitive file links for readers who should not access them.
- Personal information that is not needed for the change record.
- Unrelated message history.

If sensitive detail is necessary, store it in the appropriate secure location and summarize only the safe change in the log.

## Change log template

Use this template for a simple change log.

Change log for:
[Document, file, report, project, or process name]

Version or date:
[Version label or date]

Summary:
[One or two sentences explaining the main change]

Added:
- [New item]
- [New item]

Changed:
- [Updated item]
- [Updated item]

Fixed:
- [Correction]
- [Correction]

Removed:
- [Removed item and reason, if useful]

Pending:
- [Open item, or write None]

Notes:
- [Context, decision, or source of change, if useful]

## Example change log

Change log for:
Monthly performance summary

Version or date:
April 8, 2026 review version

Summary:
This version updates the report after the first review and prepares it for final approval.

Added:
- Added a short executive summary.
- Added a notes section for exceptions.

Changed:
- Updated the deadline from Thursday to Friday.
- Reworded the introduction for a broader audience.

Fixed:
- Corrected the March total in the summary table.
- Fixed a broken link to the source file.

Removed:
- Removed duplicate rows from the export.
- Removed internal comments before sharing.

Pending:
- Confirm the April figure before final export.

Notes:
- Most changes came from reviewer comments received on April 8.

## Quick checklist

Before sharing a change log, confirm that:

- The purpose is clear.
- Important changes are included.
- Categories are consistent.
- Entries describe outcomes, not vague activity.
- Dates and version labels are clear.
- Reasons are included for important changes.
- Completed work is separate from pending work.
- Removed items are explained when useful.
- Private information is not exposed.

## Key takeaway

A strong change log makes the history of work easy to understand. Record meaningful changes, group them clearly, explain important reasons, and separate completed work from pending items.
