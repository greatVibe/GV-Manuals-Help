# Feedback Tracking

Feedback is easier to use when it is captured clearly, grouped by topic, assigned to an owner, and turned into decisions or actions.

This guide explains how to track feedback from document reviews, project updates, meetings, customer conversations, spreadsheet checks, and team reviews.

## When to use this guide

Use this guide when you need to:

- Collect comments from several people.
- Track review notes on a document or file.
- Separate requests from suggestions.
- Decide which feedback will be accepted.
- Follow up on unresolved questions.
- Keep a record of what changed after review.
- Prepare a clean response to reviewers.

Feedback tracking is useful whenever comments might otherwise be lost in messages, meeting notes, file annotations, or separate documents.

## Capture feedback in one place

Choose one place to track the feedback for a piece of work. This can be a document, spreadsheet, task list, review table, or shared note.

The tracker should include:

- The feedback item.
- Who raised it.
- Where it applies.
- The status.
- The owner.
- The decision or action.
- Any follow-up date.

Avoid spreading review notes across several channels unless there is a clear reason.

## Record the source

A feedback item is easier to resolve when the source is clear.

Include details such as:

- Reviewer name or role.
- Date received.
- File, page, section, row, or slide.
- Meeting or conversation where it was raised.
- Link or reference to the original comment when appropriate.

Example:

Reviewer: Finance team
Location: Budget summary, row 18
Feedback: Confirm whether the total includes tax.
Date received: Tuesday

Do not rely on memory to connect feedback to the right part of the work.

## Write feedback as a clear item

Each feedback item should describe one issue or request.

Prefer:

- Add a definition for the term used in section two.
- Confirm whether the March total includes late invoices.
- Reword the opening paragraph so the audience is clear.
- Remove duplicate rows before sending the final file.

Avoid:

- Fix this section
- Needs work
- Unclear
- Review later

If one comment contains several requests, split it into separate items.

## Group related feedback

Grouping makes it easier to see patterns and avoid duplicate work.

Useful groups include:

- Content changes
- Data corrections
- Formatting changes
- Questions
- Decisions needed
- Out of scope items
- Follow-up tasks

Grouping also helps when several reviewers raise the same concern in different words.

## Use simple status labels

Status labels should show what has happened to each feedback item.

Common labels:

- New: received but not reviewed yet.
- Accepted: will be applied.
- Declined: will not be applied.
- Needs clarification: more information is required.
- In progress: currently being handled.
- Done: resolved and checked.
- Deferred: saved for later work.

Define the labels before sharing the tracker so readers understand what each status means.

## Separate feedback from decisions

Feedback is an input. A decision is what will happen next.

For each important item, capture:

- The feedback.
- The decision.
- The reason for the decision, when useful.
- The action required.

Example:

Feedback: Add a longer explanation of the process.
Decision: Declined for this version.
Reason: The guide is meant to stay short; detailed process notes will go in a separate reference.
Action: Add a one-sentence link to the reference when it is available.

This prevents accepted, declined, and deferred feedback from blending together.

## Assign owners for action items

Feedback without an owner often stays unresolved.

Assign an owner when the item requires:

- A content change.
- A data check.
- A decision.
- A customer response.
- A follow-up meeting.
- A final verification step.

For simple edits, the owner can be the person preparing the final version. For questions or decisions, assign the person who can answer or decide.

## Track due dates only when useful

Not every feedback item needs a due date. Use dates when timing matters.

Dates are useful for:

- Approval deadlines.
- Customer commitments.
- Meeting preparation.
- Launch or publishing timelines.
- Items blocking other work.

If a date is approximate, write it clearly as a target date rather than a firm deadline.

## Identify blockers early

Some feedback cannot be resolved until another person, file, or decision is available.

Call out blockers directly:

- Waiting for updated source data.
- Waiting for approval from the reviewer.
- Waiting for a missing file.
- Waiting for a decision between two options.
- Waiting for clarification of the requested change.

A blocked item should include the next follow-up action.

## Respond to reviewers clearly

When feedback is resolved, reviewers may need to know what changed.

A short response can include:

- Accepted and applied.
- Accepted with a smaller change.
- Declined, with reason.
- Deferred to a later version.
- Needs clarification before action.

Example:

Accepted with a smaller change: added a short definition in the introduction instead of a new section, to keep the guide concise.

Clear responses reduce repeated comments and confusion.

## Keep a change record

For important reviews, record what changed after feedback.

A useful change record includes:

- Item number.
- Change made.
- Date completed.
- Person who completed it.
- Verification notes, if needed.

This is especially useful when preparing final files, reports, customer responses, or version summaries.

## Avoid common tracking problems

Common problems include:

- Combining several comments into one vague item.
- Losing who raised the feedback.
- Marking feedback done before checking the change.
- Accepting conflicting feedback without a decision.
- Leaving questions without an owner.
- Keeping declined items without a reason.
- Mixing private internal notes into a shared tracker.

Review the tracker before sharing it with a wider audience.

## Protect private information

Feedback trackers can contain sensitive comments, customer details, personal information, or internal notes.

Avoid including:

- Passwords or access tokens.
- Private customer data unless required and approved.
- Personal details that are not needed for the work.
- Internal commentary that should not be shared.
- Sensitive file links for readers who should not access them.
- Unrelated message history.

If sensitive detail is required, use the appropriate secure location and summarize only what is needed in the tracker.

## Feedback tracker template

Use this template for a simple feedback tracker.

Item:
[Short item number or title]

Source:
[Reviewer, meeting, file, or comment location]

Feedback:
[One clear issue, request, or question]

Group:
[Content, data, formatting, question, decision, follow-up, or other]

Status:
[New, accepted, declined, needs clarification, in progress, done, or deferred]

Owner:
[Person responsible for the next action]

Decision or action:
[What will happen next]

Due date:
[Date if useful, or write None]

Resolution note:
[What changed, why it was declined, or what remains open]

## Quick checklist

Before closing a feedback review, confirm that:

- All feedback is captured in one place.
- Each item has a clear source.
- Large comments are split into separate items.
- Related items are grouped.
- Status labels are defined.
- Decisions are recorded separately from feedback.
- Action items have owners.
- Blockers are visible.
- Reviewers receive clear responses when needed.
- Private information is not exposed.

## Key takeaway

Good feedback tracking turns scattered comments into clear decisions and actions. Capture each item, name the source, assign ownership, and record the resolution so the work can move forward without losing important context.
