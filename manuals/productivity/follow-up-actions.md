# Follow-up Actions

A follow-up action turns a decision, review comment, meeting note, or issue into a clear next step. Good follow-up actions make work easier to finish because everyone can see what needs to happen, who owns it, and when it is due.

This guide explains how to write and track follow-up actions for productivity work, shared files, documents, spreadsheets, reviews, approvals, meetings, and project summaries.

## When to use this guide

Use this guide when you need to:

- Turn meeting notes into next steps.
- Assign work after a review.
- Track unresolved approval items.
- Convert an issue report into action.
- Capture work that must happen after a file is shared.
- Follow up on a missing answer or decision.
- Keep small tasks from being forgotten.
- Clarify who is responsible for the next step.

A follow-up action is useful whenever a note, comment, or decision requires someone to do something later.

## Write actions as outcomes

A follow-up action should describe the result that needs to exist when the work is done.

Prefer:

- Add the approval date to the summary.
- Confirm the correct total in the spreadsheet.
- Share the final PDF with the reviewers.
- Update the file name to match the naming standard.
- Move deferred items into next week's task list.

Avoid:

- Work on summary.
- Check spreadsheet.
- Handle PDF.
- Fix file.
- Follow up later.

Outcome-based actions are easier to complete and easier to verify.

## Include an owner

Every follow-up action should have one owner.

The owner is responsible for moving the action forward. The owner may ask others for help, but the action should not be assigned to everyone.

Examples:

- Owner: Project lead
- Owner: Reporting team
- Owner: File owner
- Owner: Document reviewer
- Owner: To be assigned

If the owner is unknown, write Owner needed instead of leaving the field blank.

## Include a due date when timing matters

Not every follow-up action needs a deadline, but actions tied to approval, sharing, reporting, or meetings usually do.

Useful due date formats include:

- Due: 2026-04-10
- Due: April 10, 2026
- Due: Before the next review
- Due: Before sharing externally
- Due: No fixed date

Use a consistent date format within the same list or project.

## Add context without copying everything

A follow-up action should include enough context to understand why it exists.

Useful context includes:

- The related meeting.
- The related review comment.
- The related issue report.
- The affected file or section.
- The decision that created the action.
- The reason the action matters.

Example:

Action: Confirm the correct total in the spreadsheet.
Context: The overview tab total does not match the source rows from the April 8 review.

Do not copy long message threads into the action. Link or summarize only what is needed.

## Make the requested result testable

A follow-up action should be clear enough that someone can tell whether it is done.

Testable actions:

- Add the missing approval date to the final summary.
- Replace the broken link in the review notes.
- Export the approved spreadsheet as a PDF.
- Confirm whether duplicate rows should be removed.

Hard-to-test actions:

- Improve the summary.
- Look at the link.
- Work on formatting.
- Discuss duplicates.

If an action cannot be verified, rewrite it until the result is clear.

## Use status values consistently

Simple statuses help teams scan follow-up work.

Common statuses include:

- Open: The action has not started.
- In progress: Work has started.
- Waiting: The owner needs input, access, or approval.
- Done: The action is complete.
- Deferred: The action is intentionally delayed.
- Cancelled: The action is no longer needed.

Avoid creating too many status values. A small, consistent set is easier to maintain.

## Record blockers separately

If an action cannot move forward, explain why.

Useful blocker notes include:

- Waiting for approval.
- Waiting for source data.
- Waiting for access.
- Waiting for a decision.
- Waiting for another action to finish.

Example:

Status: Waiting
Blocker: The reviewer needs access to the shared file before the link can be confirmed.

A blocker should point to what is needed next, not just say that work is stuck.

## Separate actions from decisions

A decision explains what was chosen. A follow-up action explains what must happen because of that decision.

Decision:
The monthly summary will be shared as both a spreadsheet and a PDF.

Follow-up actions:
- Prepare the spreadsheet for internal review.
- Export the approved PDF.
- Add the export date to the change log.

Keeping decisions and actions separate makes both easier to track.

## Separate actions from notes

Meeting notes and review notes often contain background information, but only some notes require action.

Example note:
The reviewer asked whether the April total includes hidden rows.

Follow-up action:
Confirm whether hidden rows are included in the April total.

Do not treat every note as an action. Only create actions for work that needs an owner or next step.

## Keep actions short

Most follow-up actions should fit in one sentence.

Include:

- Verb.
- Object.
- Owner.
- Due date, if needed.
- Context, if needed.

Example:

Confirm the correct total in the April summary spreadsheet. Owner: Reporting team. Due: April 10.

If the action needs several paragraphs, it may be a project, issue report, or decision record instead.

## Review follow-up actions regularly

Follow-up actions lose value if they are not reviewed.

Useful review moments include:

- End of a meeting.
- Start of the next meeting.
- Before sending a status update.
- Before closing a task.
- Before sharing a final file.
- During weekly planning.

During review, check:

- Is the action still needed?
- Is the owner still correct?
- Is the due date still realistic?
- Is anything blocked?
- Can the action be marked done?

## Close actions with a result

When an action is complete, record what happened.

Examples:

- Done: Approval date added to the final summary on April 10.
- Done: Reviewer access restored and link confirmed.
- Done: PDF exported from the approved spreadsheet.
- Cancelled: Action no longer needed because the report was replaced.
- Deferred: Moved to next week's planning list.

Closing with a result preserves useful history and helps future readers understand what changed.

## Protect private information

Follow-up actions are often copied into notes, summaries, and task lists.

Avoid including:

- Passwords or access tokens.
- Private customer details unless required and approved.
- Sensitive personal information.
- Internal notes that should not be shared.
- Links that readers should not be able to access.
- Long message history unrelated to the action.

If sensitive context is needed, summarize the safe action and keep sensitive details in the appropriate secure location.

## Follow-up action template

Use this template for a simple follow-up action.

Action:
[Clear outcome to complete]

Owner:
[Person or team, or write Owner needed]

Status:
[Open, in progress, waiting, done, deferred, or cancelled]

Due date:
[Date, timing note, or No fixed date]

Source:
[Meeting, review, decision, issue, or file that created the action]

Context:
[Short reason or background]

Blocker:
[Blocker, or write None]

Result:
[What happened when closed]

## Quick checklist

Before sharing follow-up actions, confirm that:

- Each action describes a clear outcome.
- Each action has one owner.
- Due dates are included when timing matters.
- Context is short and useful.
- Actions are separate from notes and decisions.
- Status values are consistent.
- Blockers explain what is needed next.
- Completed actions include a result.
- Private information is not exposed.
- The list can be reviewed later without extra explanation.

## Key takeaway

A useful follow-up action makes the next step obvious. Write the action as an outcome, assign one owner, include timing and context, track blockers, and close the action with a clear result.
